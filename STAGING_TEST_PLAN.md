## Sequence
**S0 — Backup + restore rehearsal (no traffic).** *Exact commands: `STAGING_SETUP_CHECKLIST.md` §C–E (on a fresh database the migrations run first, then this check).* `pg_dump -Fc` the staging DB; restore into a scratch DB; compare table/index/constraint/enum counts, migration rows and row counts of tenants, customers, conversations, messages, outbox, memories, jobs, appointments. *Expect* identical. *Evidence:* the comparison output + timings. *Abort:* any difference or a restore error.
**S1 — Migration rehearsal on the restored copy.** Apply 0008→0012 with `drizzle-kit migrate`; record duration; run the §3 SQL; verify legacy-retry backfill counts (`outbox_messages WHERE idempotency_key LIKE 'legacy-retry:%'` = `messages WHERE status='retry_pending'` before); run the `INBOX.md` follow-up SQL for legacy `staff_owned` rows. *Expect* no data loss, no lock > 5 s. *Abort:* any row-count diff.
**S2 — Deploy with all flags off.** `GET /health` 200; Meta webhook GET verification succeeds; **unsigned** POST ⇒ rejected (4xx); signed POST from the Meta test number ⇒ 200. TLS: certificate valid, HTTP→HTTPS redirect, `curl -sI https://…/inbox/` shows `Strict-Transport-Security`, `/api/inbox/*` unreachable over plain HTTP. *Abort:* an unsigned POST is accepted.
**S3 — Booking happy path (real model, simulated nothing: real DB + outbox + Meta sandbox).** From phone A: `I want a cleaning` → `yes` → `Tuesday 2pm` → `Trevor <phone>` → `yes`. *Expect:* exactly one `appointments` row (correct service/UTC start/customer), `messages` outbound rows `sent`, `outbox_messages.status='sent'` with a `provider_message_id`, no duplicate reply. *Capture:* SQL output + the WhatsApp screenshots.
**S4 — Corrections.** Repeat S3 with: `actually 3pm`; `nah make it 3pm instead`; `It's Alisha, not Alicia` (also curly ’); `yes, Alisha not Alicia`; `wrong number, it's <new>`; `yes, wrong number, it’s <new>`; `next week Friday at 2pm`. *Expect:* stored name/phone/time exact after each correction; **no appointment row before the separate final yes**; one row after it with the corrected values; summary re-asked after each correction. *Abort:* any wrong-data row.
**S5 — Duplicate / replayed messages.** Re-POST the **identical signed payload** (same `wamid`) 3× (and twice concurrently). *Expect:* one `messages` row for that id, one reply, one appointment; `webhook` returns 200 to Meta each time. Also send the same text twice as *different* messages ⇒ treated as two messages (document behaviour). *Abort:* a duplicate durable effect.
**S6 — Ambiguous time inputs (fix check).** After `I want a cleaning` → `yes`, send each of `Tuesday quarter to 3pm`, `Tuesday not 3pm`, `Tuesday 3pm or 4pm`, `Tuesday from 2pm to 4pm`. *Expect (fixed offline in `0bfa3c7`, **not yet live-verified**):* reply "What one time works for you?"; **no time stored**; no appointment row. Then, with a complete booking awaiting confirmation (`2pm`, name, phone), send `3pm or 4pm` ⇒ the stored `14:00` is kept but confirmation is withdrawn; `yes` ⇒ **still nothing booked**; `3pm` ⇒ new confirmation summary (still nothing booked); a separate `yes` ⇒ exactly one appointment at 15:00. Controls that must still work: `Tuesday 3 pm`, `2:30pm`, `tmrw 3pm`, `actually make it 3pm not 2pm`. Record pass/fail per message.
**S7 — Human takeover.** Start a conversation, trigger a handoff (`I want to speak to a person`). In `/inbox` (over HTTPS): login, accept, take over, then send a customer message ⇒ **no AI reply**; staff reply ⇒ delivered once, ordered; return to AI ⇒ next customer message answered. Race: takeover while a reply is being generated ⇒ suppressed. *Abort:* any AI message after takeover.
**S8 — WhatsApp delivery limits.** (a) Inside the 24-hour window ⇒ `sent`. (b) After the window (or to a number that never messaged the test line) ⇒ Meta rejects; outbox shows **Failed to send** with the provider error; manual **Retry** does *not* fix it — expected; recovery = customer writes again. (c) Delivered/read status events: confirm they are **ignored** (documented gap). *Capture:* outbox rows + the provider error code.
**S9 — Memory (`MEMORY_ENABLED=true`).** Say `My name is Alicia`, `I prefer mornings`; later `Can I book a cleaning?` ⇒ acknowledged naturally, availability still checked by the tool. Then `Forget that I prefer mornings` ⇒ preference deleted, the model does not claim transcripts were erased. *Check logs:* `{scope:"memory"}` lines contain no message text. Sensitive text (`I have diabetes`) ⇒ nothing stored.
**S10 — Background jobs (`JOBS_ENABLED=true`).** `npm run jobs -- enqueue-memory-sweep <tenant>` ⇒ completes (`result.swept`), idempotent for the day. `kill -TERM` the process during a slow job ⇒ drains and exits 0; restart ⇒ nothing lost. Pause DB connectivity ~10 s ⇒ worker logs `poll_error`, resumes, no lost job. Standalone worker: `npm run worker` against a down DB ⇒ stays alive, recovers. *Abort:* a stuck `running` job after lease expiry.
**S11 — Soak (≥ 24 h, flags on).** Light real traffic; alert on dead-lettered outbox rows, `failed` jobs, `poll_error`, 5xx.
**S12 — Rollback drill.** (1) flags off ⇒ behaviour returns to Phase 3, no job polling; (2) drop 0012/0011 objects per `RELEASE_GATE_CHECKLIST.md` §4 ⇒ app still serves; (3) restore the S0 snapshot ⇒ row counts equal S0. *Pass:* all three work.
